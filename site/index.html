boardfarmdevs · Apps labs

Downloadable applications on an RDK‑B router, in a lab that fits in one VM

RDK-B has two application frameworks: DAC, the downloadable application containers that are its default, and LCM, prpl's lifecycle management. The apps lab runs both side by side: two RDK-B routers, one per framework, each a container on its own Boardfarm WAN and LAN, into which an application is installed, started and stopped through the data model, over rbus and over USP.

An application here is a container in a container in a VM: an OCI bundle run by crun, in a router that is itself a nested LXD container, in the lab VM, on a bare-metal host.

The two frameworks

RDK default

DAC

Downloadable Application Containers. DSM manages deployment and execution units, Dobby runs them as OCI bundles with crun. It is what the apps toolkit builds unless told otherwise.

  • bpibroadband-dac Boardfarm CPE 1: dhcp-cpe1, wan-cpe1, lan-cpe1
  • Tools dsmcli, DobbyTool, rbuscli, obuspa -c

prpl

LCM

Lifecycle Management. timingila and cthulhu on the Ambiorix stack, with the same OCI bundles run by crun, selected at build time with the prpl meta-amx and meta-lcm layers.

  • bpibroadband-lcm Boardfarm CPE 2: dhcp-cpe2, wan-cpe2, lan-cpe2
  • Tools ba-cli, rbuscli, obuspa -c

Both

One data model

Either way the router presents TR-181 Device.SoftwareModules.: install a deployment unit from a URL, set an execution unit's requested state, read the execution environments.

  • rbus Device.SoftwareModules.InstallDU(), ExecutionUnit.{i}.SetRequestedState()
  • USP obuspa as the agent, and as the controller on the router itself

The life of an application

Seven steps, from a tar on the build host to a page a LAN client fetches, and back to nothing. Every step is the same data model operation whichever way it is sent: by the framework's own tool, over rbus, or over USP.

The applications

The lab's first two need neither an SDK nor a toolchain: apps/build.sh assembles them from programs of the router image itself and follows their shared libraries, so they match the router's userspace by construction. The same bundles are meant for both frameworks; so far they run on the DAC router.

3.7 MB

hello

A shell loop that prints a line every five seconds: busybox and the C library, nothing else. It has its own network namespace and talks to no one.

  • Shows that a container runs, by its output in the router's journal: hello-from-dsm #1 pid=1 host=Kn

7.3 MB

tictactoe

A web page: lighttpd with its modules and the libraries they need, serving a tic-tac-toe game on port 8090. It shares the router's network, so the page is at the router's addresses.

  • Shows an application a LAN client uses: the lab's LAN client fetches the page through the router while the application runs, and no longer after the stop

How it is built

The apps lab follows the RDK EasyMesh lab of the EasyMesh labs: the same Yocto layer, meta-cmf-bananapi-vcpe, which rebuilds the Banana Pi RDK-B broadband image for x86 as an LXD container; the same pinned upstream sources; the same Boardfarm; the same three stages. It leaves out what applications do not need (radios, the RF medium, extenders, Wi-Fi clients) and adds a second router, LAN clients and the LCM image.

Run it

On an Ubuntu 22.04 host prepared as for the EasyMesh lab (the Yocto host tools, LXD with /dev/kvm):

git clone git@github.com:boardfarmdevs/apps-labs.git ~/git/apps-labs
cd ~/git/apps-labs
export PATH="$HOME/hosttools/bin:$HOME/bin:$PATH"
build/bootstrap-sources.sh        # the Yocto workspace in yocto/, at the pinned commits
build/build-images.sh both        # the DAC and the LCM router image
lab/build.sh build                # the VM apps-lab with both routers, checked
lab/build.sh status
lab/build.sh check                # WAN, DHCP, internet, LAN, framework: per router
lab/build.sh router bpibroadband-dac        # a shell in a router

In a router, the data model the applications are managed through:

rbuscli getvalues Device.SoftwareModules.
obuspa -c get Device.SoftwareModules.
rbuscli method_values "Device.SoftwareModules.InstallDU()" \
    URL string http://10.101.0.1:8080/hello.tar ExecutionEnvRef string default
obuspa -c operate "Device.SoftwareModules.ExecutionUnit.1.SetRequestedState(RequestedState=Active)"
DobbyTool list
